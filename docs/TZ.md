# Технічне завдання (скорочено) — Система онлайн-бронювання столиків у ресторанах

Повна версія — у звіті до лабораторної роботи №1.

## Призначення

Веб-застосунок, що дозволяє гостям переглядати вільні столики й бронювати їх
онлайн, а адміністраторам ресторанів — керувати столиками, розкладом та
бронюваннями.

## Основні функції

1. Реєстрація та авторизація користувачів.
2. Пошук ресторанів і перегляд вільних слотів на дату/час/кількість гостей.
3. Створення, зміна та скасування бронювання.
4. Сповіщення про підтвердження та нагадування.
5. Адмін-панель ресторану (столики, розклад, статуси бронювань).
6. Відгуки та оцінки після візиту.

## Цільова мікросервісна структура

| Сервіс | Відповідальність | Етап появи |
| --- | --- | --- |
| `booking-service` (`backend/`) | каталог ресторанів, доступність, бронювання | 1 (зараз) |
| `frontend` (`frontend/`) | веб-інтерфейс гостя | 1 (зараз) |
| `auth-service` | реєстрація, вхід, ролі | 2–3 |
| `restaurant-service` | каталог і адмін-панель (виділяється з booking-service) | 3 |
| `notification-service` | email/SMS-сповіщення | 3 |

## DevOps-інструменти (з ТЗ ЛР1)

| Категорія | Інструмент за ТЗ ЛР1 | Етап | Стан |
| --- | --- | --- | --- |
| CI/CD | GitHub Actions | 1 | базовий CI — `booking-ci.yml` |
| Оркестрація | Kubernetes (Minikube) | 3 | заплановано |
| Модульні тести | JUnit/PyTest → для Node.js-стеку: вбудований `node:test` | 1 | реалізовано |
| API-тести | Postman/Newman | 4 | заплановано (на етапі 1 — базові API-тести на `node:test`) |
| E2E-тести | Selenium WebDriver | 4 | заплановано |
| Моніторинг | Prometheus + Grafana | 5 | заплановано (`GET /health` уже є) |
| IaC | Terraform | 4 | заплановано |
| Секрети | HashiCorp Vault | 5 | заплановано |

JUnit і PyTest у ТЗ ЛР1 названо як фреймворки модульного тестування бекенду,
але мову бекенду тоді не було зафіксовано. На етапі 1 обрано Node.js (один
рантайм для сервісів і конвеєра, без зовнішніх залежностей), тому інструментом
тієї ж категорії став вбудований у Node.js `node:test`; вибір Postman/Newman та
Selenium не змінюється — вони інтегруються на етапі 4 за планом.

## Етап 1 — план з ЛР1 і виконання

Етап 1 за планом ЛР1: «Планування та підготовка репозиторію» — закласти
структуру проєкту й базовий процес розробки. Інструменти: Git, GitHub,
GitHub Actions. Очікуваний результат: репозиторій з базовою структурою, ТЗ та
працюючим базовим CI-конвеєром.

| Робота за планом ЛР1 | Виконання |
| --- | --- |
| Створення репозиторію | публічний репозиторій `restaurant-booking-devops` |
| Визначення структури мікросервісів (auth, booking, restaurant, notification, frontend) | таблиця сервісів вище; `backend/` = booking-service, `frontend/` |
| Написання технічного завдання | цей файл (повна версія — звіт ЛР1) |
| Вибір гілкової стратегії | `docs/BRANCHING.md` |
| Базовий CI (складання й тести при кожному коміті) | `booking-ci.yml`; тести всього репозиторію також на кожен push (`matrix.yml`) |

Понад план етапу 1 розроблено першу версію сервісів, щоб базовому CI було що
перевіряти:

1. `booking-service`: REST API (каталог, перевірка доступності, створення,
   скасування та історія бронювань) з правилами: тривалість бронювання 2 год,
   заборона подвійного бронювання столика, вибір найменшого відповідного
   столика, робочі години ресторану.
2. `frontend`: сторінка бронювання з клієнтською валідацією форми.

Для Node.js без етапу компіляції «складання» в базовому CI — це синтаксична
перевірка всіх модулів (`node --check`); повноцінне складання Docker-образів
сервісів — етап 2.
