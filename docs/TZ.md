# Технічне завдання (скорочено) — Система онлайн-бронювання столиків у ресторанах

Повна версія — у звіті до лабораторної роботи №1.

## Призначення

Веб-застосунок, що дозволяє гостям переглядати вільні столики й бронювати їх
онлайн, а адміністраторам ресторанів — керувати столиками, розкладом та
бронюваннями.

## Основні функції

1. Реєстрація та авторизація користувачів.
2. Пошук ресторанів і перегляд вільних слотів на дату/час/кількість гостей.
3. Створення, зміна та скасування бронювання.
4. Сповіщення про підтвердження та нагадування.
5. Адмін-панель ресторану (столики, розклад, статуси бронювань).
6. Відгуки та оцінки після візиту.

## Цільова мікросервісна структура

| Сервіс | Відповідальність | Етап появи |
| --- | --- | --- |
| `booking-service` (`backend/`) | каталог ресторанів, доступність, бронювання | 1; етап 2 — контейнер і PostgreSQL; етап 3 — Kubernetes з HPA |
| `frontend` (`frontend/`) | веб-інтерфейс гостя | 1; етап 2 — контейнер з Nginx; етап 3 — Kubernetes за Ingress |
| `auth-service` | реєстрація, вхід, ролі | наступні ітерації розробки |
| `restaurant-service` | каталог і адмін-панель (виділяється з booking-service) | наступні ітерації розробки |
| `notification-service` | email/SMS-сповіщення | наступні ітерації розробки |

План ЛР1 розбиває на етапи DevOps-процес (репозиторій і CI, контейнеризація,
оркестрація, тести й IaC, моніторинг і секрети) і не відводить окремого етапу
під розробку решти сервісів. Тому етапи виконуються на двох наявних сервісах,
а інфраструктура будується з розрахунком на додавання нових: у Docker Compose
і Helm-чарті новий сервіс — це ще один блок сервісу з власним образом.

## DevOps-інструменти (з ТЗ ЛР1)

| Категорія | Інструмент за ТЗ ЛР1 | Етап | Стан |
| --- | --- | --- | --- |
| CI/CD | GitHub Actions | 1 | базовий CI — `booking-ci.yml`; з етапу 2 — `containers.yml` |
| Контейнеризація | Docker, Docker Compose, GitHub Container Registry | 2 | реалізовано |
| Оркестрація | Kubernetes (Minikube), Helm | 3 | реалізовано: `deploy/helm/restaurant-booking` |
| Модульні тести | JUnit/PyTest → для Node.js-стеку: вбудований `node:test` | 1 | реалізовано |
| API-тести | Postman/Newman | 4 | заплановано (на етапі 1 — базові API-тести на `node:test`) |
| E2E-тести | Selenium WebDriver | 4 | заплановано |
| Моніторинг | Prometheus + Grafana | 5 | заплановано (`GET /health` уже є) |
| IaC | Terraform | 4 | заплановано |
| Секрети | HashiCorp Vault | 5 | заплановано |

JUnit і PyTest у ТЗ ЛР1 названо як фреймворки модульного тестування бекенду,
але мову бекенду тоді не було зафіксовано. На етапі 1 обрано Node.js (один
рантайм для сервісів і конвеєра, без зовнішніх залежностей), тому інструментом
тієї ж категорії став вбудований у Node.js `node:test`; вибір Postman/Newman та
Selenium не змінюється — вони інтегруються на етапі 4 за планом.

## Етап 1 — план з ЛР1 і виконання

Етап 1 за планом ЛР1: «Планування та підготовка репозиторію» — закласти
структуру проєкту й базовий процес розробки. Інструменти: Git, GitHub,
GitHub Actions. Очікуваний результат: репозиторій з базовою структурою, ТЗ та
працюючим базовим CI-конвеєром.

| Робота за планом ЛР1 | Виконання |
| --- | --- |
| Створення репозиторію | публічний репозиторій `restaurant-booking-devops` |
| Визначення структури мікросервісів (auth, booking, restaurant, notification, frontend) | таблиця сервісів вище; `backend/` = booking-service, `frontend/` |
| Написання технічного завдання | цей файл (повна версія — звіт ЛР1) |
| Вибір гілкової стратегії | `docs/BRANCHING.md` |
| Базовий CI (складання й тести при кожному коміті) | `booking-ci.yml`; тести всього репозиторію також на кожен push (`matrix.yml`) |

Понад план етапу 1 розроблено першу версію сервісів, щоб базовому CI було що
перевіряти:

1. `booking-service`: REST API (каталог, перевірка доступності, створення,
   скасування та історія бронювань) з правилами: тривалість бронювання 2 год,
   заборона подвійного бронювання столика, вибір найменшого відповідного
   столика, робочі години ресторану.
2. `frontend`: сторінка бронювання з клієнтською валідацією форми.

Для Node.js без етапу компіляції «складання» в базовому CI — це синтаксична
перевірка всіх модулів (`node --check`); повноцінне складання Docker-образів
сервісів — етап 2.

## Етап 2 — план з ЛР1 і виконання

Етап 2 за планом ЛР1: «Контейнеризація» — підготувати сервіси до розгортання
в ізольованому відтворюваному середовищі. Інструменти: Docker, Docker Compose,
GitHub Container Registry. Очікуваний результат: набір Docker-образів
мікросервісів у реєстрі, `docker-compose.yml`.

| Робота за планом ЛР1 | Виконання |
| --- | --- |
| Написання Dockerfile для кожного мікросервісу | `backend/Dockerfile` (booking-service), `frontend/Dockerfile` (Nginx зі статикою) |
| Налаштування docker-compose для локальної розробки | `docker-compose.yml`: db (PostgreSQL, том `booking_data`, healthcheck) → booking-service → frontend, залежності з `condition: service_healthy` |
| Оптимізація образів (multi-stage build) | обидва Dockerfile багатоетапні: тести на етапі build, у runtime — лише потрібні файли; booking-service ≈ 194 МБ проти ≈ 1,58 ГБ в одноетапного образу на `node:20` |
| Публікація образів у реєстр | `containers.yml`: тест стека в Compose, потім публікація `ghcr.io/danilara7/booking-service` і `booking-frontend` (теги: коміт, гілка, `latest` для main) |

Щоб у Compose-середовищі дані бронювань зберігалися між перезапусками,
booking-service отримав сховище в PostgreSQL (`backend/src/repo/postgres.js`,
схема — `backend/db/init.sql`); in-memory сховище лишилося для модульних
тестів і запуску без Docker. Опис цієї БД у Terraform — етап 4, керування
паролем через Vault — етап 5; до того пароль задається змінними середовища
(`.env`, не комітиться).

## Етап 3 — план з ЛР1 і виконання

Етап 3 за планом ЛР1: «Оркестрація» — забезпечити автоматичне розгортання,
масштабування та відмовостійкість. Інструменти: Kubernetes, Minikube, Helm.
Очікуваний результат: застосунок, розгорнутий у Kubernetes-кластері з
автомасштабуванням.

| Робота за планом ЛР1 | Виконання |
| --- | --- |
| Написання Kubernetes-маніфестів (Deployment, Service, Ingress) | Helm-чарт `deploy/helm/restaurant-booking`: Deployment і Service для booking-service та frontend, StatefulSet з томом і Secret для PostgreSQL, Ingress з TLS для `booking.local` |
| Розгортання в тестовому кластері | локально — Minikube; у CI (`kubernetes.yml`) — кластер kind на кожну зміну: встановлення чарта, `helm test`, димовий тест, перевірка збереження даних |
| Налаштування Horizontal Pod Autoscaler для сервісу бронювання | HPA booking-service: 2–6 реплік, ціль — 60 % CPU від requests; перевірено навантажувальним тестом |

Відмовостійкість забезпечують кілька реплік сервісів, readiness/liveness-проби
(booking-service не готовий без БД, але не перезапускається через її
недоступність — окремий `/health/live`), rolling update без зменшення кількості
робочих подів і PersistentVolumeClaim для даних PostgreSQL. Пароль БД
генерується Helm і зберігається в Secret (до переходу на Vault на етапі 5).
